# Architecture, animation pipeline and risks

## 1. What the requirements actually demand

| Requirement | Technical consequence |
| --- | --- |
| Cartoon look, not pixel art, crisp on phones and 4K | Vector-sourced art, rasterised per device resolution; GPU transforms |
| Articulated characters, real walk cycles, no sliding cut-outs | A skeleton: bone hierarchy, keyframed clips, IK for planted feet |
| Blinking, talking, head turns, idles, reactions *at the same time* | **Layered** animation: base clip + additive procedural layers |
| Hoses, coat tails, hats, tank fluid | Secondary motion: springs and rope simulation |
| Night cabin, glowing eyes, reading lights | Per-part tinting by local light, additive glow sprites, blend modes |
| Expressive camera | Camera with easing, leads, group framing, scripted moves |
| Dialogue with timing | DOM overlay (crisp text, accessibility), speech bubbles anchored to the world |
| Inspect and replay key sequences | Clips and cutscenes must be **deterministic functions of time**, so they can be scrubbed |
| Later replacement by authored art | Art format must match what artists export; animation must not depend on how parts were drawn |
| Desktop and mobile, no paid services | Static site; open-source runtime; no SaaS editor required |

## 2. Recommendation

**PixiJS v8 (WebGL) for rendering + our own small animation runtime + SVG rig sheets as the art format.**
No game framework, no GSAP.

```
          ┌─────────────────────────────────── authoring ───────────────────────────────────┐
          │  Rig sheet (SVG, one per character, rest pose, one <g id="part:…"> per part)   │
          │  today: generated by code (src/characters/*/sheet*.ts)  later: by an artist     │
          └──────────────────────────────┬──────────────────────────────────────────────────┘
                                         │ rasterise each part → atlas (scale picked per device)
┌──────────────────────── runtime ───────▼──────────────────────────────────────────────────┐
│ Rig: bones (hierarchy, rest transforms) ← parts (sprites with pivots)                     │
│ Live vector features: eyes, ICH letters, LEDs (Graphics), hoses (MeshRope)                │
│                                                                                            │
│ Animator (per character, evaluated every frame, pure function of time + state):           │
│   base layer   : keyframed clip, cross-faded (idle, sit, gestures, gags)                  │
│   locomotion   : procedural gait → foot targets → 2-bone IK (no foot sliding)             │
│   additive     : talk accents; live features: blink, look-at, expression parameters      │
│   secondary    : springs (coat, hat, head lag), Verlet ropes (hoses), fluid slosh         │
│                                                                                            │
│ Sequence (cutscenes): setup + timed events (code), stepped with the world at fixed dt    │
│   → re-simulating from t=0 is deterministic → Animation Lab can scrub, slow down, replay  │
│ Story script: async/await (walkTo, say, choose, play(sequence)) for interactive flow      │
│ UI: DOM/CSS overlay (bubbles, choices, case file, menus, lab controls)                    │
└────────────────────────────────────────────────────────────────────────────────────────────┘
```

### Why PixiJS v8
- Fast 2D scene graph on WebGL with batching; mobile-proven.
- Exactly the primitives this game needs: `MeshRope` for bending hoses, a pre-baked radial glow texture
  with additive blending for light, and inherited container tint for scene lighting. (The magnifier
  close-up is a DOM/SVG overlay, not a render texture.)
- Rendering only. It does not impose a game structure we would have to fight.

### Why not Phaser
It is a good engine (the KA-III prototype uses it), but its strengths (arcade physics, tilemaps, its own
scene system) are not needed here, and its Graphics API is weaker for curved vector work.
For a character-animation-driven adventure the renderer underneath matters more than the framework on top.

### Why not SVG in the DOM (+ GSAP)
It would be the simplest way to get crisp vectors, and SVG is still our *art format*. But animating
~150 transformed nodes per frame plus glow filters through the DOM is slow on mid-range phones
(SVG filters are CPU-rendered), and there is no cheap way to bend a hose.

### Why not GSAP
GSAP (free since 2024) is excellent for UI and fire-and-forget tweens. Our cutscenes, however, must be
*scrubbable* together with the characters' own clip time, IK and springs. Bridging GSAP timelines to a
custom animator would be more code than our ~100-line sequence player (setup + timed events, re-simulated
from t = 0 to seek).
UI micro-animation is done in CSS.

### Why not Spine, Rive, DragonBones, Live2D
- **Spine** is the industry standard for skeletal 2D, but its editor is paid. Our rig model (bones,
  slots, attachments, clips with curves) intentionally mirrors Spine's, so moving to Spine later is a
  data migration, not a rewrite. `pixi-spine` exists.
- **Rive** requires its online editor. **DragonBones** is unmaintained. **Live2D** is aimed at
  front-facing portraits, not full-body adventure acting.

## 3. Animation asset pipeline

### 3.1 Today (prototype)
1. **Rig sheet.** Each character is described as an SVG document in its rest pose, one `<g>` per part:
   `<g id="part:forearm.near">` (alternative drawings are marked `data-alt`; a `data-bone` attribute is
   written for orientation only and is not read). The SVG is *generated by code*
   (`src/characters/<id>/sheet*.ts`), which is how the placeholder art is drawn.
2. **Atlas build.** At load time each part is rasterised once (texel density chosen per device: 1.0–2.2×
   the 1080p reference) and packed into atlas pages per character. On 4K/dpr-2 screens, cutscene
   close-ups above about zoom 1.1 upscale the raster parts slightly (the live vector features stay crisp).
3. **Bones and draw order.** The rig definition (`src/characters/<id>/index.ts`, plus
   `ich/variantB.ts` and `ich/variantC.ts`) defines the hierarchy, the rest pivots (in the same
   coordinate system as the sheet, so the rest pose renders exactly like the drawing) and each slot's
   bone and z order.
4. **Live features.** Eyes, ICH's letters, LEDs and hoses are drawn every frame as vector graphics or
   meshes, because they change shape, not just position.
5. **Clips.** Keyframed in TypeScript (`src/characters/*/clips.ts`): per-bone rotation/offset/scale
   channels with easing curves, plus expression and event keys. Locomotion is procedural (IK gait).
6. **Export.** The Animation Lab can download every rig sheet as `.svg`, the template an artist
   starts from.

### 3.2 With authored art (the path to final quality)
1. An artist draws each character **on top of the exported rig sheet** in Inkscape, Illustrator or
   Affinity Designer, keeping the part groups and their ids, and saves it to `art/authored/<id>.svg`.
   The loader prefers an authored sheet when one exists. No code change.
2. Raster artists (Krita, Photoshop, Procreate) would export one PNG per part plus its sheet-space
   rectangle (pivots come from the rig); a small importer, **planned, not written yet**, would produce
   the same atlas records (the format is documented in `src/anim/atlas.ts`).
3. Clips that need drawn extremes (smears, squash keys, special poses) get **swap parts**: alternative
   drawings for the same slot, keyed in the clip. The runtime supports part swaps already.
4. If the team buys Spine later: export bones and clips to Spine JSON (planned script), keep the same
   part names, play through `pixi-spine`.

### 3.3 What needs authored art, concretely
| Asset | Why procedural is not enough |
| --- | --- |
| Final character art for all three (rig-sheet redraw, ≈ 35–45 parts each) | Clean, characterful line work and painted shading; the procedural art is geometric |
| Front view, back view and true profile for each character, plus head turnarounds | A 3/4 cut-out rig cannot turn convincingly beyond about ±45° without new drawings |
| Hand pose library (≈ 12 poses each: point, fist, open, grab, thumbs, facepalm…) | Hands are where the acting is; procedural fingers are stiff |
| Smear and squash frames for the big gags (avalanche, trip, R-3MI's seat attempts) | Hand-drawn exaggeration is what makes slapstick feel animated, not puppeted |
| ICH's final design sheet and expression sheet (after the A/B/C decision) | The design is not final |
| Background paintings (cabin, galley, lavatory) | The procedural cabin is clean but lacks texture and storytelling details |
| Voice: optional German voice cast, or at least designed "babble" voices | Synthesised babble is a placeholder |
| Music: the detective theme | The synthesised motif is a sketch |

## 4. Biggest risks

| # | Risk | Mitigation |
| --- | --- | --- |
| 1 | **Procedural art and animation have a quality ceiling.** Geometric parts and code-keyed motion will never look like hand-drawn animation. | The pipeline is built so authored art drops in without code changes. The prototype is honest about what is placeholder ([STATUS.md](STATUS.md)). |
| 2 | **Cut-out turnarounds.** 3/4 rigs look flat when they turn. | Today a turn is a quick (0.16 s) whole-body squash through an edge-on moment; V-TGM's eye is projected on her sphere, the other features are flat. Head-leading turns, squash drawings and front/back views need authored art (on the list). |
| 3 | **ICH's legibility** during mirroring, turns, falls. | Letters are a separate vector layer that is never mirrored and is covered at most partially and briefly. On a landscape phone they are about 22–26 CSS px tall (camera zoom 0.85–1), checked on renders; there is no automatic minimum size yet. |
| 4 | **Comic timing** needs iteration and real audiences. | Clips are keyframe data and cutscenes are timed event lists in code; both can be inspected in the Lab at 0.1–0.25× speed, and tuning means editing the TypeScript files. Playtests needed. |
| 5 | **Mobile performance** (atlas memory, additive glow fill rate). | Atlas scale adapts to the device; glows are pre-rendered sprites; one blur filter remains (the ending's passing shadow). Layout and touch are checked on an emulated phone viewport; performance has not been measured yet, real devices are still to be tested. |
| 6 | **Canon fidelity.** Existing art is a pair of flattened paintings; the rig art is a re-interpretation. | Silhouette, colours, key features **and handedness** taken directly from the portraits (R-3MI's had been mirrored and was corrected, see [STATUS.md](STATUS.md)); side-by-side check in the Lab's lineup (*Aufstellung*). Team sign-off needed. |
| 7 | **Language rule.** The brief asks for German dialogue; canon says V-TGM speaks English. | Canon wins: V-TGM speaks English with a German subtitle. Needs explicit confirmation. |
| 8 | **The secret ending** must be fair but invisible. | Clues are environmental and deniable; no line states the truth. Documented in a spoiler file for the team only. |
| 9 | **Scope creep** (a whole plane of guests). | Chapter 0 uses three characters and anonymous sleepers only. |
| 10 | **Repository** separation from Kalibrierungsanlage III. | Own repository (`Team-Aperture/mega-mysterious-murder-of-r3mi`); KA-III is never touched. |
